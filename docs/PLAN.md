## 0. 一句话定位

仓颉解决了"把知识变成 skill"，入世要解决的是更难的三个问题：
**让 skill 自证可信、让 skill 可测效果、让 skill 随真实使用而进化。**

---

## 1. 软件 Fellow 视角：我们到底在造什么

10x 程序员的第一课：**不按功能清单思考，按杠杆点思考。**

这个项目真正的杠杆点有四个：

1. **Schema 即真相（Schema as Source of Truth）**
   一份规范同时驱动文档、校验器、CLI、CI 与测试生成。改动规范 = 全系统同步进化，而不是改 N 个散落文件。这是第一个 10x 杠杆。

2. **证据链即信任基础设施（Provenance as Trust Infrastructure）**
   仓颉的"已验证"是自我声明；入世的"已验证"必须指向可审计的证据包（原文 span、校验记录、测试报告）。信任一旦可验证，就变成基础设施，可以被任何人复用，而不是依赖作者人格。

3. **评测即护城河（Evaluation as Moat）**
   谁拥有"效果评测基准 + 真实反馈数据"，谁就拥有持续改进的飞轮。技能包是消耗品，评测与数据是复利资产。

4. **进化闭环即复利机器（Evolution as Compounding）**
   每个包的使用反馈回流后修正引擎与包本身——系统越用越强，而不是越用越旧。这正是"入世"和"仓颉"的本质区别：**知识必须入世接受检验，再回炉重炼。**

### 设计信条（Fellow's Credo）

1. **消灭一类问题，而不是修一个问题**——忠实度校验 + 证据链，消灭"幻觉不可审计"这一整类问题。
2. **先让系统自证，再宣称有效**——所有"已验证"必须链接证据，无证据即无徽章。
3. **简单到难以犯错**——默认本地、纯文本 skill、无状态流水线、CI 强制闸门。
4. **机器做重复验证，人只做高杠杆判断**——人工只保留抽样审计、rubric 评审、进化审批。
5. **开发者体验即产品**——一条命令端到端；错误信息必须可行动。
6. **不造第二个框架**——复用生态，适配层兼容 Claude Code / Cursor / Codex。
7. **好度量先于好功能**——每个阶段有明确的通过/不通过标准，先有尺子再做活。
8. **让资产复利**——每次蒸馏既产出包，也回填引擎；每季度必须变强一次。

## 2. 终极目标（North Star）

**愿景**：把"知识蒸馏"升级为"知识入世"——不再问"我们产出了多少个 skill"，而是问"这些 skill 在真实世界里被调用后，是否让人的决策与产出变得可证明地更好"。

**v1.0 里程碑定义**：入世是一个开源的、自验证、可进化的 Agent Skill 生产系统：

- 输入：书 / 长视频转写 / 播客 / 课程 / 内部文档
- 输出：带完整证据链、通过机器可验证忠实度检查、带效果评测、可一键安装、可持续进化的 skill 包
- 闭环：真实调用反馈（触发日志、结果评分、误用报告）自动回流，驱动 trigger 与边界修正

**北极星指标**：`Skill 效果增量 = 使用入世包的任务成功率 − 基线（不用包）任务成功率`，目标 ≥ +20%（专家盲评口径），随每个发布包公开。

**辅助指标**：

| 指标 | 目标 |
|---|---|
| 引用忠实度（机器校验 + 人工抽样） | 幻觉率 < 0.5%，抽查引文 100% 可溯源 |
| 触发精度 / 召回（基准集） | Precision ≥ 95%，Recall ≥ 90% |
| 全流程时效（文本 → 可安装包） | ≤ 48h，其中人工审查 ≤ 2h |
| 进化活跃度 | 每包每季度 ≥ 1 条有效提案，人工采纳率 ≥ 70% |

## 3. 仓颉问题 → 入世设计支柱

| # | 仓颉短板（实证） | 根因 | 入世支柱 | 落地机制 |
|---|---|---|---|---|
| 1 | 验证自我指涉 | 提取/验证/出题/判卷同一模型 | 他证化（Grounding-first） | Provenance DB + 检索式忠实度校验 + 异模型交叉 + 留出法测试 + 人工抽样审计 |
| 2 | 书内一致 ≠ 外部正确 | V1 奖励重复、V3 奖励反常识 | 外部三角验证 | 独立信源佐证；置信度分级（author-claim / empirically-supported / unverified） |
| 3 | 测触发不测效果 | 测试只查 would_trigger | 效果优先评测 | A/B 基准任务 + rubric 专家盲评 + 生产遥测 |
| 4 | 标签式溯源 | 引用只标年份 | 机器可验证溯源 | claim ID + source span + 原文哈希 + "数字必须带出处"规则 |
| 5 | 原子化碎片 | 单 skill 安装，共享上下文断链 | Pack 级上下文 | pack.json 整体安装；GLOSSARY/INDEX/关系图随包；workflow 复合 skill |
| 6 | 自检清单当闸门 | 无自动化 gate | 发布闸门自动化 | CI：schema 校验、链接解析、artifact 完整性、证据包强制 |
| 7 | 前提未验证 | 无基准实验 | 基准先行 | 基准套件 + 基线对照；先测后宣 |
| 8 | 静态过时 | 无版本/维护/过期机制 | 生命周期管理 | semver + freshness + 过期策略 + 进化闭环（人类审批门） |
| 9 | 成本不可控 | 5 agent 全量跑 | 分层执行 | fast/slow lane + 缓存 + 抽样验证 + 每包预算上限 |

## 4. 产品定义

- **是什么**：一个"元技能 + 引擎 + CLI + 注册表"的完整系统。入世自身也是一个 skill——用户说"把 X 蒸馏成入世 skill"，即可跑通全流程。
- **不是什么**：不是摘要工具；不是提示词集合；不是又一个 skill 列表站点。
- **用户**：深度知识工作者（投资/咨询/创作者）；团队知识沉淀；企业私域方法论（内部文档 → 团队可调用 skill）。
- **价值主张**：装一个入世包 = 获得"可追溯、已测试、有证据、会进化"的方法论，而不是一段好看的 Markdown。

## 5. 系统架构

```
┌─ 输入层 ──────────────────────────────────────────┐
│ 书/PDF/EPUB · 视频字幕 · 播客转写 · 内部文档      │
│ 内容清单: 源哈希 + 分块(≤5万字) + 元信息 + 脱敏钩子│
└──────────────┬────────────────────────────────────┘
┌─ 蒸馏核心（流水线 v2，10 阶段）───────────────────┐
│ S0 摄入 → S1 理解 → S2 并行提取 → S3 忠实度校验   │
│ S4 外部验证 → S5 构造 → S6 链接 → S7 评测         │
│ S8 打包安装 → S9 发布闸门                         │
└──────────────┬────────────────────────────────────┘
┌─ 证据与数据层 ────────────────────────────────────┐
│ Provenance DB(SQLite) · 基准套件 · 测试报告       │
│ 遥测存储(本地优先) · 失败案例库                   │
└──────────────┬────────────────────────────────────┘
┌─ 运行时与反馈 ────────────────────────────────────┐
│ 安装适配器(Claude/Cursor/Codex) · 触发日志        │
│ 反馈通道(👍/👎/误用报告) · 结果评分               │
└──────────────┬────────────────────────────────────┘
┌─ 进化闭环 ────────────────────────────────────────┐
│ 提案生成 → 人类审批门 → 回归测试 → 发版 → 过期调度│
└───────────────────────────────────────────────────┘
```

### 核心组件职责

| 组件 | 职责 | 关键技术 |
|---|---|---|
| `rushi-core` | 流水线编排、状态机、断点续跑 | Python 3.11+，无状态，幂等 |
| `rushi-verifier` | 忠实度校验：引用 → 原文 span；事实/数字 → 出处核对 | 确定性匹配 + LLM-as-judge + 人工抽样 |
| `rushi-eval` | 触发测试 + 效果 A/B + 多模型盲测 | 基准套件 JSONL + rubric 模板 |
| `rushi-pack` | 打包、依赖解析、冲突检测、安装适配 | pack.json + semver + 适配器接口 |
| `rushi-cli` | 开发者体验入口 | `rushi distill/verify/test/package/install/evolve` |
| `rushi-registry` | 注册表 + 证据徽章（链接证据包） | 静态站 + CI 发布 |
| `rushi-evolve` | 遥测 → 提案 → 审批 → 发版 | 规则 + LLM 提案 + 人类 gate |

## 6. 核心规范设计

### 6.1 入世包结构（pack）

```
rushi-pack/
├── pack.json            # name, version, source, license, confidence, freshness
├── PROVENANCE.md        # 每条 claim 的证据链（claim id / span / quote / checker / 置信度）
├── TEST_REPORT.md       # 触发测试 + 效果测试 + 多模型盲测结果（发布硬性附件）
├── GLOSSARY.md          # 共享术语（随包安装，解决断链）
├── INDEX.md             # 关系图（机器生成 + 人工确认）
├── workflows/           # 复合 skill（原子组合成流程，可选）
└── skills/<slug>/
    ├── SKILL.md         # 入世 schema v2
    └── tests/
        ├── trigger.json # 应触发/诱饵/边界（升级版，含跨包混淆）
        └── outcome.json # 效果基准任务 + 评分 rubric
```

### 6.2 SKILL.md v2 frontmatter

```yaml
name: slug
description: 触发条件（自动生成 + 遥测修正，中英双写）
version: 0.1.0
source: { title, author, year, span_id }
confidence: author-claim | empirically-supported | unverified
related: [{ slug, relation, direction, weight }]
freshness: { checked_at, expires_at, policy }
telemetry: { enabled, feedback_channel }
```

### 6.3 蒸馏流水线 v2（10 阶段，每阶段有确定性 gate）

| 阶段 | 动作 | 确定性 gate（不通过即打回） |
|---|---|---|
| S0 摄入 | 哈希、分块、元信息、脱敏检查 | 源哈希入库，分块完整 |
| S1 理解 | Adler 四步 + 机器可检查清单 | 批判 ≥3 条、术语 ≥5 条 |
| S2 并行提取 | 5 路提取器，候选带 source span | 每条候选有 span 引用 |
| S3 忠实度校验 ★ | 逐条核对 R 引用与 A1 事实；数字必须带出处 | 引文匹配率 100%；无法核对 → 降级/删除 |
| S4 外部验证 ★ | 跨来源佐证 → 置信度分级 | 每 skill 有 confidence 字段；未佐证不得标 empirically-supported |
| S5 构造 | RIA++ 六段 + 触发指纹 + 判停分支 | 六段完整、description ≤300 字且含"何时不用" |
| S6 链接 | 自动关系发现 + 人工确认 | 所有 related slug 可解析；无孤儿引用 |
| S7 评测 ★ | 触发测试 + 跨 skill/跨包混淆 + 多模型盲测 + 效果基准 | 精度/召回达标；test-results 落盘 |
| S8 打包安装 | 依赖解析、冲突检测、适配器 | 目标宿主可加载验证 |
| S9 发布闸门 | CI 全量检查 + 证据包归档 | artifact 完整；TEST_REPORT 存在；徽章链接证据 |
| S10 进化 | 遥测 → 提案 → 审批 → 回归 → 发版 | 旧测试全过 + 新增测试 |

### 6.4 评测体系（三级）

1. **触发评测**：unit 级，测 precision/recall，含跨 skill、跨包混淆诱饵。
2. **效果评测**：任务级 A/B（带包 vs 不带包），rubric 专家盲评；先覆盖可评分任务（文案、投资分析、决策清单、学习诊断）。
3. **生产遥测**：opt-in、匿名、本地优先；记录调用率、误用率、反馈分；仅汇总数据回流进化。

### 6.5 进化闭环

- **输入**：遥测异常、误用报告、过期提醒、新资料
- **提案**：修改 trigger / 边界 / 步骤 / 置信度，附带修改理由与证据
- **审批**：人类 gate + 回归测试（旧用例全过）
- **发版**：semver + CHANGELOG + 可回滚

## 7. 实施路线图（M0–M4）

### M0 立项与 PoC（第 1–2 周）

- 交付：repo 骨架；四份 JSON Schema v0.1（skill / pack / claim / test）；**忠实度校验器 PoC**（1 份文本 + 50 条引用做 span 匹配 + 人工核对）；10 个基准任务模板；CI 骨架
- 验收：PoC 引用定位召回率 ≥ 90%，误报率 ≤ 10%

### M1 MVP（第 3–8 周）

- 交付：流水线 v0.1（S0–S8）；`rushi-cli` 端到端；**第 1 个入世参考包**（内容源由用户指定）；触发基准 v0.1（每 skill ≥ 10 题）
- 验收：参考包全部 claim 有证据链；触发精度 ≥ 90%；TEST_REPORT 可审计

### M2 评测与反馈闭环（第 9–16 周）

- 交付：效果基准 v1（20+ 任务 + rubrics）；A/B harness；遥测 SDK + 本地仪表盘；反馈通道；进化引擎 v0.1
- 验收：完成基线对照并发布首个效果报告；进化提案 ≥ 5 条且人工采纳 ≥ 3 条

### M3 规模化与生态（第 17–28 周）

- 交付：Claude / Cursor / Codex 适配器；私域文档管道（权限 + 脱敏）；注册表（徽章链接证据包）；依赖解析与冲突检测；成本分层

- 交付：贡献规范（含证据要求）、CI 自动审查、年度重蒸馏调度、公开基准榜
- 验收：外部贡献 ≥ 5 包且全部过闸门；基准榜公开

## 8. 关键技术决策与取舍

1. **栈**：Python 3.11+（引擎）+ JSON Schema（规范）+ SQLite（证据/遥测）+ GitHub Actions（CI）。选成熟无聊的技术，把复杂度留给方法论本身。
2. **忠实度校验两级制**：确定性 span 匹配优先；语义核对（数字/事实）用 LLM-as-judge + 人工抽样。不信任任何单模型结论。
3. **效果评测小步走**：先做"任务级 rubric"，不宣称通用提升；分领域发布效果数据。
4. **触发机制升级**：description 之外加"触发指纹"（话语模式向量），用遥测修正；skill 保持纯文本、无运行时代码侵入，遥测走 opt-in 钩子。
5. **安装模型**：pack 级优先，单 skill 降级支持；目录约定中性化，不锁死任何宿主。
6. **隐私合规**：默认本地处理；外部验证只发送必要片段并明示；注册表只发布元数据 + 证据哈希；AGPL-3.0。
7. **明确不做**：不做运行时 agent 框架；不做闭源商业化；不做完全无人监督的自动发布（人类 gate 是底线）。

## 9. 风险与对策

| 风险 | 概率/影响 | 对策 |
|---|---|---|
| 幻觉仍漏过校验 | 中/高 | 双级校验 + 人工抽样 + 失败即降级（unverified），闸门 fail-closed |
| 效果评测做不出来 | 中/高 | 从可评分任务起步；分域发布；承认局限 |
| 成本超限 | 中/中 | 分层执行、缓存、抽样；每包预算上限 |
| 生态锁定/格式分裂 | 中/中 | 中性 schema + 适配器；对齐 agentskills 标准 |
| 用户不反馈 | 中/低 | 遥测轻量可关；用"误用报告"而非问卷 |
| 私域内容泄露 | 低/高 | 本地优先、脱敏钩子、权限清单、审计日志 |
| 单模型依赖 | 中/高 | 校验与蒸馏分离模型；评测多模型 |
